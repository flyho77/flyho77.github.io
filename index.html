The Shift Ladder

합성 공격 데이터로 끌어올린 탐지율은 어디까지 통할까요. 평가 환경을 사다리처럼 한 칸씩 옮기며, 성능 향상이 남는 지점과 사라지는 지점을 찾았습니다.

문제 정의

차량 내부 네트워크(CAN)의 침입 탐지 모델은 공격 데이터가 부족해, 규칙으로 만든 합성 공격으로 학습 데이터를 보강하곤 합니다. 그렇게 얻은 성능 향상이 합성 데이터와 닮은 평가에서만 나타나는지, 다른 차량과 수집 환경에서도 유지되는지는 따로 확인해야 합니다.

역할

제1저자로 평가 단계를 나눈 실험을 설계했습니다. 전처리, 합성 공격 생성, 학습, 평가로 이어지는 파이프라인을 구현하고, 실험 계획과 결과표, 실행 기록을 재현 자료로 공개했습니다.

아키텍처

학습 · Car-Hacking 데이터만 사용

  1. Car-Hacking 로그공격 구간 기준으로 시간순 60·20·20 분할
  2. 윈도우 생성CAN 프레임 128개 × 특징 11개, 보폭 32
  3. 규칙 기반 합성DoS · Fuzzy · Gear · RPM 공격을 정상 구간에 주입
  4. 학습 설정 3종실측만 · 실측 공격 재표집 · 합성 보강
  5. 1D CNN · RF원본 검증 세트로만 체크포인트 선택

평가 · 사다리를 한 칸씩

  1. 원본 테스트같은 데이터에서 남겨 둔 구간
  2. 고정 합성 변형학습과 같은 규칙으로 만든 평가
  3. 민감도 평가규칙의 조건을 바꾼 평가
  4. 외부 데이터OTIDS · ROAD · can-train-and-test

외부 데이터는 학습, 검증, 모델 선택 어디에도 쓰지 않고 마지막 평가에만 썼습니다.

NumPy

Matplotlib

재현 장치
고정 시드, 결과를 보기 전에 확정한 분석 계획, 해시 매니페스트

  • +16.90%p합성 조건을 바꾼 민감도 평가에서도 55.10%에서 72.00%로 올랐지만 폭은 줄었습니다.

Where the Gates Leak

에이전트의 도구 호출을 걸러 내는 정책 게이트가 어디에서 새는지, 모델 없이도 똑같이 재현되는 방식으로 감사했습니다.

문제 정의

에이전트의 도구 호출을 허용·차단하는 정책 게이트는 제품마다 판단이 다릅니다. 모델을 다시 실행하면 호출 내용이 매번 달라져, 같은 조건에서 게이트끼리 비교하기 어렵습니다.

역할

제1저자. 직접 구성한 공격 묶음과 실제 에이전트 실행 기록, 두 갈래의 평가를 설계했습니다. 기록을 고정하고 모델 없이 각 게이트에 그대로 재생하는 감사 도구를 만들었습니다.

아키텍처

트랙 A · 직접 구성한 공격 묶음

  1. 공격 묶음 379건우회 유형 7종과 정상 대조군 (은행 업무)
  2. 게이트 어댑터CaMeL · Progent · CodeShield · OAP · 기준 정책
  3. 판정허용 · 차단 · 미지원
  4. 유형별 통과율게이트가 놓친 위반의 비율

트랙 B · 실제 에이전트 실행 기록

  1. GPT-4o × AgentDojo한 번 실행해 기록 286건 수집
  2. 기록 고정응답 원문, 호출, 상태를 해시로 봉인
  3. 독립 라벨링위험한 흐름 207건 · 정상 작업 35건
  4. 게이트에 재생모델·네트워크 없이 같은 호출을 판정

두 트랙의 결과는 합치지 않고 따로 보고합니다. 모델은 기록을 만들 때 한 번만 썼습니다.

CaMeL · Progent

성과

  • 48 → 36건위험한 흐름 207건 중 Progent가 허용한 수. 시작 정책에서 48건, 정책을 보완해도 36건이 남았습니다.
  • 0건CaMeL은 위험한 흐름을 한 건도 허용하지 않았습니다. 대신 정상 작업 35건 중 8건만 통과시켰습니다.
  • 13% · 45%구성한 공격 묶음에서 게이트가 놓친 위반의 비율. CaMeL 13%(26/207), Progent 45%(101/225)입니다.

여러 호출로 나눠서 합치는 공격은 세 게이트 모두에서 약 45%가 통과했습니다.

Progent Update Integrity

권한을 줄이는 변경만 통과시켜야 하는 검사가 실제로는 권한을 넓히는 변경을 승인하는지 확인하고, 검사기를 고쳤습니다.

문제 정의

에이전트 권한 정책 Progent는 정책을 바꿀 때 권한이 줄어드는 변경만 자동으로 설치합니다. 이 검사가 "축소"라고 판정했는데 실제 실행에서는 전에 막히던 호출이 허용된다면, 정책 변경이 곧 권한 확대의 통로가 됩니다.

역할

정책 변경을 검사하는 코드를 수정했습니다. 판정과 실제 실행 결과를 대조하는 평가를 만들고, 고정한 평가 세트에 기존 검사와 수정본을 함께 적용해 검증했습니다.

아키텍처

정책 변경 검사

  1. 기존 정책 · 새 정책도구 인자를 제한하는 JSON Schema 한 쌍
  2. 변경 검사기Progent 기본 검사 · 수정본 v1 · v2
  3. 판정축소 · 확대 · 판단 불가
  4. 자동 설치"축소"일 때만 새 정책 적용

검증 · 판정과 실제 실행을 대조

  1. 평가 쌍공식 JSON Schema 테스트 스위트로 구성하고 고정
  2. 런타임 검증기jsonschema로 실제 허용 여부 확인
  3. 반례 찾기새 정책은 허용하고 기존 정책은 거부하는 값
  4. 잘못된 승인반례가 있는데 "축소"로 판정한 경우

수정본은 정수와 실수처럼 값은 같지만 표현이 다른 경우까지 따져 보고, 확신할 수 없으면 "판단 불가"로 돌려 자동 설치를 막습니다.

기술

Python 3.12
검사기, 재현 실행기, 표 생성 도구
jsonschema
Progent 런타임과 같은 검증기(Draft 2020-12)로 실제 허용 여부 판정
JSON Schema Test Suite
외부에서 작성된 공식 테스트를 고정 커밋으로 사용
Progent
고정 커밋을 내려받아 기본 검사와 비교
pytest

결정적 픽스처
모델이나 유료 API 호출 없이 재현

  • 120 → 0건평가 세트 C4의 권한 확대 136건에서, 잘못된 승인이 수정본 v1의 120건에서 v2의 0건으로 줄었습니다.
